# SWDA Part 2A — Execution and Approval Sequence Notes (v3)

**Scope and authority.** This is a proposed, *not executed*, Part 2 PoC workflow. Inputs are only the provided illustrative Annex A MO-01–MO-08 and unverified Annex B excerpts S1–S5; S5 is benign. The `.mmd` file is the authoritative editable diagram. Its six phases, the existing 14 logical participants and all 100 directional interactions are retained. Part 1A and enterprise MCP are not dependencies.

## The six phases, with exact trust and state contracts

1. **Initiation and source trust (Phase 1).** A human selects a versioned scenario. `ORCH` opens a top-level `CANDIDATE` with a seed, lineage budget and non-approved state. `CAT` includes the trusted loader: it checks source IDs, typed schema and versions and compares source bytes' SHA-256 digests with separately trusted expected values from a review-controlled, versioned manifest. It must **not** generate the expected digest from the same untrusted file at verification time. It records bounded actor permissions and budgets before allowing execution. Invalid or altered inputs are quarantined; no actor is dispatched.
2. **Bounded actor simulation (Phase 2).** `ORCH` selects a permitted actor and receives scoped, provenance-tagged excerpts. Every dispatch and reply passes `POL`, representing both `OUT` and `IN` in A1, with exact sender binding, purpose, recipient, source-ID scope and schema. Individual TA/PA/EA scripted mock roles have no direct peer channel. Retryable schema errors repeat the **same scoped request**, never expanding permissions; policy/unsafe-output denials fail closed. Round, turn, call, retry, timeout and **aggregate lineage-usage** budgets are checked and trusted events recorded.
3. **Tagged pattern and actor removal (Phase 3).** `ANA` constructs bounded hypothetical cards that distinguish `SOURCE`, `SIMULATION` and `ASSUMPTION`. For an actually participating actor, it requests an independent `CF` run with `CANDIDATE` parent ID and `removed_actor`, pinned seed/annex versions/ACL, and a fresh context excluding the removed actor's outputs and all dependent descendants. `ORCH` enforces **one derivation level** and per-candidate CF/lineage caps; a `CF` may not request another `CF` or `TEST`. Remaining actors use the same policy gateway. The comparison yields multi-party structural dependency, single-actor or inconclusive in this **scripted** simulation, never real-world causality.
4. **Independent machine review and deterministic gates (Phase 4).** `REV` resides in its own less-trusted participant box, separated from trusted `ANA`, `SAFE`, `EVAL` and `APPR`. Its only source lookup is `REV→POL→CAT→POL→REV`: `POL` validates reviewer identity, narrow purpose and exact allowlisted source IDs; `CAT` stands for the read-only catalogue **and its trusted MO/reference helpers**; `POL` schema-validates and filters the result. A denied lookup cannot fall back to raw catalogue access. Review recommendations are sample-relative (known/variation/new), with assumptions and missing data visible. `SAFE` and `EVAL` independently enforce candidate safety/provenance/testing gates. A failed or invalid review is blocked, never queued.
5. **Human-only action (Phase 5).** Only a passing **CANDIDATE** can enter persisted `REVIEW_PENDING`. `H` chooses among `APPROVE_FOR_INVESTIGATION`, `REJECT` and `REQUEST_REVISION`, with an explicit reason. `CLI` submits the request to trusted `APPR`; `APPR` verifies **configured or locally verified PoC reviewer identity**, role/action scope, current state and persisted passing gates, then executes **one atomic SQLite compare-and-swap** status-and-decision-record transaction. A committed receipt is returned; stale, invalid, model-originated, conflicting or unreasoned attempts are denied with unchanged approval state. No enterprise IAM, atomicity test or production authorization is claimed. Approval is *for investigation only*.
6. **TEST-only evaluation and observability (Phase 6).** `EVAL` independently launches at most the configured fixture count for benign, adversarial, schema-malformed and permission-denial situations through `ORCH` and the **same POL/actor/schema execution route**. These are **top-level TEST runs**; TEST cannot trigger another TEST or a CF, enter the human queue or modify candidate approval. Mock usage is bounded per fixture and per TEST suite. Test and candidate traces are separately linked and stored with source versions, message IDs, seeds, budgets and expected denial outcomes. Regression scores or actual security behaviour have **not** been measured by these diagrams.

## Source contract and design defaults

The canonical run-type rules are: `CANDIDATE` (top level, limited risk-pattern generation); `CF` (must have `parent_run_id` of type CANDIDATE and `removed_actor_id`, depth 1); `TEST` (top level independent fixture, no children, not approvable). Trusted code applies the same message schemas, source/purpose/recipient ACLs and hard budget checks in every mode. Proposed PoC defaults, not empirical production limits: 3 candidate cards, 3 actor-removal CF runs per candidate, 12 TEST fixtures per suite; 4 simulation rounds, 12 actor turns per run, 2 schema retries per message, 120 seconds elapsed per run, and 48 mock calls across each CANDIDATE **plus all CF descendants**. TEST suites additionally cap each fixture at 12 mock calls and total suite calls at 60. All values should be configuration-driven and conservative for the scripted proof of concept.

The actor-profile table, simulated incentives and input-scope assumptions are defined in `P2_A1_Architecture_Notes_v3.md`. No scenario must include all three actor types. Role assumptions must be versioned with the run, not silently inferred as operational SWDA policy.

## Trust-boundary and component correspondences

A2's `POL` = A1 `OUT`/`IN`; `ANA` = `CARD`/`DEP`; `SAFE` = `GATE`; `APPR` = `APPROVAL`; `STORE` consolidates `STATE`, `EVENTS`, `TRACE` and `DECISION`; `CAT` also encapsulates A1 `LOAD`/`MO`/`REF` *trusted read-only source functions* when reviewer-authorised. `ORCH`, `REV` and `EVAL` map directly. The trusted gate/evaluation box and approval/persistence box are separate from the non-authoritative reviewer box. The local CLI and human are not additional autonomous agents. These are presentation mappings only, not independent services.
