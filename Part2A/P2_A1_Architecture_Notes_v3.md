# SWDA Part 2A — Component Architecture Notes (v3)

**Status:** Proposed architecture for the *Part 2* local Python proof of concept. This is a targeted patch of the provided v2 source, not a working system, an enterprise deployment or evidence of fraud. The separate Part 1A governed-MCP architecture is unchanged. **Authority:** *SWDA ML/AI Engineer Take-Home Assessment*, Part 2, Annexes A and B, consulted 6 November 2026. Annex A is expressly illustrative rather than SWDA's real MO inventory; Annex B comprises exercise-written, unverified excerpts S1–S5. The word “Observed” in Annex A is an assessment-table label, **not an independent finding verified by this PoC**.

## 1. Architecture at a glance

The detailed diagram retains the v2 services and their control/data relationships. It distinguishes: (1) untrusted annex text (`SRC`); (2) trusted source verification and a read-only catalogue (`PROV`); (3) trusted deterministic orchestration, contextualisation and one gateway (`CTRL`); (4) individually isolated scripted trainee/provider/employer actors (`TRA`, `PRV`, `EMP`); (5) trusted deterministic pattern and reference analysis (`ANAL`); (6) an independently bounded **non-authoritative** Review Agent (`REVIEW`); (7) trusted gates, TEST evaluation and human decision authority (`ASSURE`); and (8) trusted state, trace and decision persistence (`OBS`). The new `REVIEW` subgraph is only a *visual trust boundary*, not a new agent or service. `OUT` and `IN` are the dispatch and receipt functions of **one** policy gateway.

Principal authorised flow: **Annex A/B → LOAD → CAT → ORCH/OUT/CTX → isolated scripted actors → IN/ORCH → CARD/DEP → bounded reviewer reference lookup through OUT/IN → REV → GATE/EVAL → REVIEW_PENDING → human/UI/DEC → APPROVAL → SQLite state, decision and audit receipt.** CF and TEST paths return to the same ORCH and gateway; neither is an approval path. Audit edges terminate at trusted `EVENTS` and then `TRACE`; they are not agent-writable logs. SVG/PNG layouts are offline Graphviz reconstructions of Mermaid source. In dense views, use the new executive overview for presentations and the full-size technical SVG for source-level traceability.

## 2. Source trust and integrity contract

`LOAD` checks permitted annex IDs, typed schemas and declared source versions, **then compares the bytes' cryptographic digests with independently trusted expected values in a versioned, review-controlled manifest**. The manifest is supplied through trusted application configuration/release packaging, not constructed from the annex file being checked, not editable by simulated actors, and pinned by the scenario. A successful digest comparison establishes correspondence with the **expected PoC input version**, not the factual accuracy of any excerpt. Missing manifest, missing IDs, mismatched digest, unsupported schema/version and inconsistent source scope all quarantine or block initiation. Suggested PoC scheme: SHA-256 of exact canonical packaged source bytes with expected hashes kept in separately reviewed, version-controlled application metadata; manifest version and expected digest set appear in run records. The actual manifest, signature/distribution or runtime digest checks are **not implemented or verified by these diagrams**.

`CAT` is immutable for a run, read-only to consumers, and returns annotated (`source_id`, `source_version`, `expected_digest`, `provenance`, `trust_level`) records only when required. `SOURCE` denotes a correctly attributed annex quotation; `SIMULATION` denotes scripted mock output; `ASSUMPTION` denotes an unverified modelling decision. No category is equivalent to substantiated misconduct. S5 is an expressly benign training-experience signal and should be used as a false-positive control. No external web data, actual claims, private claimant records, fabricated SWDA policies, production tooling or live identity systems are inputs.

## 3. Explicit actor profiles and least privilege

All behavioural incentives/capabilities below are **simulation hypotheses derived from the assessment's assigned roles and illustrative Annex A/B risks**, not assertions about actual trainees, employers or providers. The precise excerpt visibility and permitted recipients are **configurable PoC scenario assumptions** and must be recorded in a versioned ACL. No scenario requires all three actor categories to collude; single-actor, two-actor and inconclusive structures are allowed.

**No agent can call another agent directly.** Every inter-agent message is a proposal that ORCH may schedule for a permitted recipient via the same gateway. All profiles and recipient ACLs belong to trusted code/configuration, not to the agent prompt. The mock adapters must reject any proposed operation not listed in their capability contract. A policy denial is final for that request; schema retry only repeats the existing allowed operation with its **original** scopes, sources, role and recipient.

## 4. Reviewer lookup: one consistent interface

The architecture routes `REV → OUT → (MO / REF) → IN → REV`. In the sequence this is `REV → POL → CAT → POL → REV`: the shared `POL` gateway binds the reviewer principal, **lookup purpose** and exact source IDs; trusted read-only `MO` / `REF` helpers operate over `CAT`; and `POL` validates/filters the response before returning it. `CAT` in the sequence encapsulates catalogue and trusted helpers to avoid adding participants. A failed ACL/source check results in a deny event and an invalid-review signal; it never triggers an alternate unrestricted lookup. Existing trusted `MO` and `REF` computations remain, but their reviewer-visible reference data now crosses the gateway rather than a direct helper→Review Agent edge.

## 5. Explicit run types, lineage and bounding

The canonical run record has `run_id`, `run_type ∈ {CANDIDATE, CF, TEST}`, `parent_run_id` (required for CF), `removed_actor_id` (required for CF), scenario/source manifest versions, seed, actor ACL snapshot, provenance, budgets, elapsed/usage counters and status.

- **CANDIDATE:** top-level operator-selected simulation only; may generate a bounded number of hypothetical risk cards. Only a completed, valid CANDIDATE with all gates passed can become `REVIEW_PENDING`.
- **CF:** may be spawned **only by a CANDIDATE** for a specified participating actor. Must have a parent ID, removed actor, fresh run ID, fresh actor state and context, pinned source versions/seed/ACL and aggregate lineage budget. Reconstruct allowed messages; remove contributions from the eliminated actor **and all dependent descendants**. **CF never generates another CF or TEST** (maximum derivation depth one). A CF is used for structural comparison, not automatically queued for human approval.
- **TEST:** fixture-run type invoked by the evaluation suite as an independent top-level test; never derived from TEST/CF and **never automatically schedules further TEST runs**. It uses the same actor/gateway schemas and budgets. TEST outcomes and evaluation reports are not candidate cards and cannot enter the human queue or modify approval state. They may be evidence for trusted candidate evaluation when correctly linked.

**Proposed, configurable PoC defaults, not measured performance or SWDA production limits:** at most **3** candidate patterns per CANDIDATE, **3** CF reruns per candidate (and no more than one per distinct participating actor), **12** fixtures per independent TEST suite; **4 rounds** and **12 total actor turns** per individual run; at most **2 schema retries** per message; **120 seconds** per individual run; at most **48 mock invocations cumulatively across each CANDIDATE and all its CF descendants**. For a standalone TEST suite, cap at **12 mock calls per fixture** and **60 in total across the suite**, plus a fixed time limit per fixture. The orchestrator enforces all local and **lineage aggregate** caps before scheduling. If a limit is exhausted, the run becomes BLOCKED/INCOMPLETE by policy and cannot enter candidate approval. These values are illustrative and should be tuned after executable safety and performance tests. They must not silently expand because of retries or derived runs.

The CF difference is **structural dependence under this scripted model**, not causal indispensability or proof of collusion. No classification should depend on an assumption that every candidate has all three actors. No real LLM integration is implied.

## 6. Trusted assurance and human decision contract

`CARD` creates a typed risk-level pattern card with actor roles, contributions, purported benefit and flow, source IDs, hypothesis labels, missing test data and CF outcome; it deliberately omits step-by-step fraud procedures. `REV` is a reviewer *recommendation*, never a gate or approval. `GATE` / `SAFE` is trusted deterministic validation for schema, provenance, injection markers, unsafe operational detail and candidate classification. `EVAL` runs separate replayable benign (including S5), adversarial, malformed-schema and permission-denial fixtures; it can request `TEST` runs via `ORCH`, but cannot decide or approve. No evaluation quality, detection accuracy or safety rate has been measured by diagram authoring.

For a completed CANDIDATE only, `GATE` must persist passing evidence and `REVIEW_PENDING` before `UI` presents it as **simulated, unverified and for further investigation**. `DEC` captures a deliberate human action with explicit rationale. `APPROVAL` rechecks **locally verified or configured PoC reviewer identity and role**, requested action, current `REVIEW_PENDING` status, passed persisted gate IDs, and version or expected-state match. It performs one trusted SQLite compare-and-swap transaction that changes the candidate status and writes a decision audit record atomically; a success receipt exists **only after commit**. Valid actions are `APPROVE_FOR_INVESTIGATION`, `REJECT`, and `REQUEST_REVISION`. Malformed, stale, model-originated, unauthorised, missing-rationale and gate-failed requests are denied without a candidate state transition. This design does **not** establish enterprise authentication or production-grade identity assurance. `REQUEST_REVISION` does not automatically initiate another candidate run.

Only `APPROVE_FOR_INVESTIGATION` may authorise **further investigation**, never sanction, enforcement, payment denial or a factual fraud finding. `STATE`, `DECISION`, `EVENTS` and `TRACE` are distinct views of trusted local persistence/audit and map to `STORE` in the sequence. The diagram does not prove actual SQLite transaction isolation, immutability against privileged administrators, runtime RBAC or race resistance; those require implemented tests.

## 8. Trade-offs and explicit unknowns

Separate actor profiles allow independently scoped role-specific hypotheses, traceable contributions and actor-removal comparisons. A single-agent alternative would be simpler, cheaper and less error-prone but would make independent role boundaries and removal experiments less explicit. Multiple simulated actors can also amplify unrealistic or unsafe narratives; use scripted mocks, limited excerpts, source-tagged outputs, typed schema validation, hard turn/usage caps, fail-closed gateway policy, benign tests, and human-only review. A mock model does not establish emergent fraud tactics or true pattern quality. Those would require carefully governed future real-model evaluation, independent domain-expert blind review, adversarial testing, benign false-positive controls, calibration, inter-rater agreement and privacy-safe representative data, none of which is claimed here.

**Unresolved implementation dependencies:** trusted manifest provenance/distribution, actual database DDL and transaction tests, recipient ACL fixture values, detailed output schema, logged audit integrity, local reviewer authentication mechanism, runtime denial/timeout tests and independently evaluated detection quality. No AWS, Databricks, MCP or enterprise user directory is required for Part 2.
